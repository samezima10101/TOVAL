## コードから確認した問題・検証候補

### R01 / P1: 不正データの初期状態扱い

**2026-10-15実装**: 不正JSON・スキーマ不合格・未対応版はPreservedDataErrorとして通常操作/移行保存を拒否し、主キー原文を保持する。再読込、対象と影響の確認後の退避・初期化を提供。退避に失敗すれば初期化しない。旧形式の不正フィールドの黙示補正も停止した。メモリストレージの補助確認済み、M17/M18の実機操作は未検証。以下は改修前の調査記録。

**事実**: JSON不正、現行スキーマ検証失敗、未対応バージョンでparseはnull、loadは初期状態を返す。読み込めないデータのバックアップ・破損通知はない。日記1件の不正でも全体が検証失敗になり得る。

**推測**: 利用者には履歴が消えたように見え、続けてタスク保存すると元JSONが上書きされて回復しにくくなる。

**次の改善候補**: 無効データを保全して復旧選択を提供し、移行・破損ケースの保持内容を確認する。根拠: [parsePersistedState/load/parseDiaryLogs](../../src/storage/appStateRepository.ts)。

### R02 / P1: 自動停止の保存失敗と強制終了

**2026-10-15実装**: 停止は保存より先に同期反映し、保存中の停止を古い結果で戻さない。失敗通知と再試行を用意し、再試行成功まで停止、成功後の現在時刻から再開する。保存済み累積を再起動後も維持し、不明区間は補填しない。最後の停止以降の未保存区間の損失はA04で許容。定期保存は追加していない。M15/M16は実機未検証。以下は改修前の調査記録。

**事実**: 自動停止/再開は保存成功後に状態反映。AppStateとフォーカス経由の失敗はcatchで捨てる。タイマーの累積を定期チェックポイント保存せず、再起動ではrunningSinceを単にnullへ変える。

**推測**: 停止保存が失敗してrunningSinceが残ると、背景時間を区間へ含める可能性がある。一方、強制終了では最後に確定した区間以降の時間を失う可能性がある。

**次の改善候補**: 保存失敗時の安全な計測状態と通知、許容損失、再起動復旧を決め、対象OSで確認する。根拠: [applyTimerEligibility/normalizeHydratedState](../../src/state/AppStateProvider.tsx)、[フォーカス管理](../../src/hooks/useTimerLogic.ts)、[pauseTimer](../../src/domain/timer.ts)。

### R03 / P1: 「全画面表示」の判定範囲

**2026-10-15実装・判定基準**: A01を適用し、iPhoneのAppState activeかつタイマー画面focusedを計測条件とする。inactive/backgroundとルート離脱で停止し、黒画面Modalのみでは停止しない。再開保存失敗時は資格が戻っても再試行まで停止。Androidのblur/分割画面や省電力効果は今回の判定対象外。M04〜M07のロック・通知パネル・Modal等は実機未検証。以下は旧α要件を含む調査記録。

**事実**: 判定に使うのはNative AppStateのactiveとRouterフォーカスだけ。ウィンドウの大きさ・分割画面状態・Android blurイベントは判定しない。黒画面で画面ロック防止や輝度低下は行わない。

**推測**: α要件の「全画面表示外なら停止」を全端末のマルチウィンドウで満たすとは限らない。「省電力」は表示上の意図であり、消費電力の改善量は未計測。

**次の改善候補**: 全画面の定義を明確にし、分割・通知パネル・OS自動ロック・黒画面中の計測を実機確認する。根拠: [Provider](../../src/state/AppStateProvider.tsx)、[タイマー](../../app/timer.tsx)、[α要件](../α版要件定義.md)。

### R04 / P1: 環境不一致とlint不合格

**事実**: ローカルTypeScript/型定義/lint設定がlockと異なり、expo-modules-core直下も欠ける。lintはルール未定義5件、型チェックは旧ローカルバージョンでのみ成功。

**推測**: 別環境で型・lint・起動結果が変わる可能性がある。現状の型チェック成功を正式な環境での合格と解釈できない。

**次の改善候補**: 採用SDKを決定し、依存を再現できる環境で再検証する。根拠: [検証結果](development-operations.md)、[package](../../package.json)、[lock](../../package-lock.json)。

### R05 / P2: 日付変更とホームの案内

**2026-10-15実装**: A03に合わせローカル0時・active復帰・30秒の時計再確認で当日表示を更新。当日初回前/当日解放済み/現行全話解放済みの案内を分けた。現行3話の全解放後ロジックは補助確認、0時更新・表示のUI/実機確認と全14話での確認は未実施。[検証記録](../manual-acceptance-checklist.md#date-record-alignment)。以下は改修前の調査記録。

**事実**: ホームの今日判定は描画時のtodayKey。日付更新用タイマーやAppStateによるホームの再描画要求はない。また同日完了後も「次の完了で…解放」と表示する。

**推測**: ホームを表示したまま0時を跨ぐと完了表示が残り得る。案内を見て当日もう一度完了しても話が解放されず、期待と異なる。

**次の改善候補**: 日付変更時の表示更新と、当日解放済みの場合の案内を仕様に合わせる。根拠: [ホーム](../../app/index.tsx)、[nextUnlockedStory](../../src/domain/completion.ts)。

### R06 / P2: 時計・日付変更への依存

**推測**: 時計を進めると過大な時間/NT、戻すと計測遅延、日付を往復すると想定外の話解放が起き得る。

**次の改善候補**: オフラインアプリで許容する範囲を決める。まず通常利用で時計変更が起きた時の計測と表示を確認する。根拠: [timer.ts](../../src/domain/timer.ts)、[completion.ts](../../src/domain/completion.ts)、[date.ts](../../src/domain/common/date.ts)。

**次の改善候補**: Q07/Q08を決めてログ項目・表示・保持方針を整備し、既存ログを壊さない移行を用意する。根拠: [DiaryLog](../../src/domain/common/types.ts)、[完了](../../src/domain/completion.ts)、[LogModal](../../src/components/log/LogModal.tsx)、[Repository](../../src/storage/appStateRepository.ts)。

## 次に取り組む順序の提案

1. **開発環境と完成基準を確定する**: Q01/Q05。文書と依存を一致させ、正しい環境でlint/型/起動を確認する。
2. **記録と計測を守る**: Q02〜04。破損保全、保存失敗、停止/復旧条件を仕様化し、必要な修正と確認を行う。
3. **日付と記録の意味を揃える**: Q06〜08。0分、日次判定、ログ項目、タスク変更、ホーム案内を決める。
4. **既存の会話・購入・遷移を完成させる**: Q09/Q11/Q12。前半の会話・購入・遷移は実装済み、実機未検証。後半のBGM・回帰確認が残っており工程全体は未完了。
5. **配布手順を整備する**: Q10。対象端末で検証し、製品ビルドと公開の手順を確定する。
6. **追加機能を選ぶ**: Q13。話数追加、イベント、休憩等を優先順に進め、仕様と移行を更新する。

この順序は追加機能の量より先に、現在の記録と利用体験を確実にするための提案。今回の作業範囲は調査・文書化まで。
