■ 1. プロジェクトの基準を確認する

最初にAGENTS.mdと、対象に適用される配下のAGENTS.mdを読んでください。

以下を確認し、今回の変更に関係する仕様・制約・検証項目を特定してください。

- docs/completion-criteria.md：仕様・対象範囲・合格条件
- docs/development-operations.md：環境・検証コマンド
- docs/manual-acceptance-checklist.md：関連する手動確認と現在の検証状況

対象に応じて以下も参照してください。

- 状態・保存・移行：docs/data-integrations.md
- 会話・購入・価格・入荷条件：docs/conversation-settings.md
- BGM：docs/bgm-settings.md
- フォント：docs/font-settings.md
- 関連するdocs/verification/の検証記録

コードを書く前に、AGENTS.mdの指示に従い、必ずExpo SDK 57の版指定ドキュメントを読んでください。
https://docs.expo.dev/versions/v57.0.0/

過去の検証記録を現在の確認結果として扱わないでください。
文書とコードに食い違いがあれば、仕様・実装・過去の記録を区別し、今回の判断根拠を示してください。

■ 2. 対象ファイルと他ファイルの連携を調べる

対象ファイルを全文読み、役割・状態・副作用・公開している契約を把握してください。

import先だけでなく、このファイルを利用している側も検索してください。
以下を含めて確認してください。

- import、export、再export、型の参照
- パスエイリアス、動的import、require
- Expo Routerのファイルベースルートと文字列での画面遷移
- Provider／Context、カスタムフック、共有状態
- 設定・コンテンツのID参照、アセット読み込み
- 関連ドキュメントからの参照

単純なimport検索で見つからないことだけを理由に、未使用と判断しないでください。

関係するファイルは実際に読み、props、引数、戻り値、非同期処理、エラー処理、保存や画面遷移の順序まで確認してください。
影響が伝わる範囲を追い、無関係なファイルの精査には広げないでください。

編集前にgitの差分を確認し、既存の未コミット変更を保持してください。

■ 3. 変更の必要性を判断する

次の観点で、根拠のある改善だけを選んでください。

- 現在の仕様に不要な機能や分岐
- 到達しないコード、不要な状態、重複処理
- 将来の仮定だけのために存在する抽象化や拡張機構
- UI・業務判断・永続化・副作用の混在
- 独立した責務として分離すると理解しやすくなる箇所
- 分割しすぎて処理の流れを追いにくくしている箇所

行数の多さだけで分割せず、短くすること自体を目的にしないでください。
コンポーネント化・フック化・関数抽出は、責務や状態の所有者が明確になり、読む側の負担が減る場合に行ってください。
既存の適切な実装を活用し、不要な共通化、汎用コンポーネント、大量のprops、新しい依存は追加しないでください。

改善が不要なら、理由を示して変更なしで完了してください。

■ 4. 必要な変更を実施する

調査結果と変更方針を短く説明したうえで、必要な修正を実施してください。
対象ファイルを中心とし、呼び出し元・参照先・ドキュメントの修正は整合性を保つために必要な範囲に限定してください。

以下を維持してください。

- 完成基準で定めた機能とユーザーに見える動作
- import／export、型、ルート、呼び出し側との整合性
- 保存成功後に業務状態を確定する原則と、計測停止の即時反映などの例外
- 保存キュー、失敗通知、再試行、破損保全、旧形式の移行
- 保存済みデータ、会話・分岐・商品の識別ID、解放・購入済みの権利
- タイマーの計測条件、日付判定、報酬、日記、画面遷移の順序
- BGMの再生条件、フォント、表示、操作性

エラー処理、連打防止、保存中の制御、ライフサイクル処理、旧データ互換は、複雑に見えるという理由だけで削除しないでください。
UIで使われていない保存項目も、移行や互換性を確認せず削除しないでください。

分割でReactの再マウント、状態の初期化、Effectの再実行、古い値の参照、購読の重複が起きないようにしてください。

仕様変更や新機能は今回のリファクタリングに混ぜないでください。
独立した不具合や仕様判断が必要な問題は、根拠とともに別途報告してください。

■ 5. 検証する

AGENTS.mdと完成基準A10に従い、自動テストは追加・復元しないでください。

変更後に差分と参照関係を見直し、少なくとも以下を実行してください。

- npm run lint
- npm run typecheck

依存・設定・アセット・ファイル分割などの影響に応じて、開発運用手順に従い以下も実行してください。

- npm run deps:check
- npm run doctor
- npm run bundle:ios

コマンド失敗時は、今回の変更による問題と既存・環境由来の問題を区別してください。
診断を通すための無関係な依存更新やチェック抑制は行わないでください。

手動チェックリストから必要な回帰確認を特定してください。
PCの静的診断やiOSバンドル生成だけで、iPhone実機の受け入れ合格とは判断しないでください。
実施していない確認は「未実施」としてください。

実装の説明・ファイル参照・確認手順が変わった場合は、対応するdocsを必要最小限更新してください。過去の検証結果は書き換えず、今回の結果を区別して記録してください。

■ 6. 結果を報告する

最後に以下を簡潔に報告してください。

1. 対象ファイルの役割と、確認した主な連携先
2. 実施した変更と、その必要性
3. 削除・分割を見送った主な箇所と理由
4. 変更したファイル
5. 実行した検証と結果
6. 残る手動確認・未解決事項

問題を指摘するときはファイルパスと該当箇所を示してください。
推測は推測として明示し、実施していない確認を成功と報告しないでください。
